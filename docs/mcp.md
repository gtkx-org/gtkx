# MCP server

`@gtkx/mcp` is a Model Context Protocol server that lets an AI agent inspect and drive a running gtkx application. It exposes a fixed catalog of MCP tools to an AI client over stdio, and bridges each tool call to a live app over a Unix-domain socket using a newline-delimited request/response protocol.

The package owns only the server and protocol/transport side. The matching client — the part that attaches a running app and answers requests — lives in the gtkx CLI dev runner (`packages/cli/src/mcp`) and reuses the protocol types and transport exported from this package.

## Two servers in one process

`createMcpServer` wires together two distinct server roles:

- An MCP `McpServer` (server name `gtkx-mcp`) that talks to the AI client over `StdioServerTransport`. This is the front: it advertises the `gtkx_*` tool catalog and receives tool calls.
- A `SocketServer` bound to a Unix socket that gtkx apps connect to. This is the back-channel: every tool call is translated into a request sent to a connected app.

`start()` opens the listening socket, then connects the `McpServer` to stdio. `stop()` closes the socket and the MCP server, and is idempotent. `main()` constructs the server, installs a graceful-shutdown handler (from `@gtkx/utils`) that calls `stop()` on signals, and starts it. The `bin/gtkx-mcp.js` executable is a thin wrapper that imports and runs `main()`.

`createMcpServer`, `McpServerHandle`, and `main()` live in `server.ts` and are internal to the package: they are consumed by the bin wrapper, not re-exported from the package index. See [Package surface](#package-surface) for what is importable from `@gtkx/mcp`.

Diagnostics are written to **stderr**, never stdout. Stdout is reserved for the MCP stdio protocol, so all logging uses `console.error`.

## Inverted client/server roles

The transport role and the request-initiation role are deliberately opposite:

- The gtkx **app** is the socket **client** — it dials the Unix socket.
- The MCP **server** is the request **initiator** for every widget and app operation.

The app only ever *sends* two methods to the server: `app.register` and `app.unregister`. Everything else (`widget.getTree`, `widget.query`, `widget.click`, …) flows server → app, and the app responds. `ServerRequestParamsSchemas` enumerates the methods the app must implement, and the app-side dispatcher rejects any method outside that set with a method-not-found error.

## Wire protocol

The IPC protocol is newline-delimited JSON (NDJSON). Each line is one message, either:

- a **request** `{ id, method, params? }`, or
- a **response** `{ id, result? }` or `{ id, error: { code, message, data? } }`.

`id` is a random UUID generated by the side that issues the request; the responder echoes it so the initiator can correlate. Both message shapes are validated by Zod (`IpcRequestSchema` / `IpcResponseSchema`). The same protocol runs symmetrically on both ends — the server initiates widget requests, but the app initiates registration, so each side both sends requests and answers them.

`DEFAULT_SOCKET_PATH` is the rendezvous point: a file named `gtkx-mcp.sock` under `XDG_RUNTIME_DIR`, falling back to the OS temp directory.

### Methods

| Method | Direction | Params |
| --- | --- | --- |
| `app.register` | app → server | `{ applicationId, pid }` |
| `app.unregister` | app → server | — |
| `app.getWindows` | server → app | — |
| `widget.getTree` | server → app | — |
| `widget.query` | server → app | `{ queryType, value, options? }` |
| `widget.getProps` | server → app | `{ widgetId }` |
| `widget.click` | server → app | `{ widgetId }` |
| `widget.type` | server → app | `{ widgetId, text, clear? }` |
| `widget.fireEvent` | server → app | `{ widgetId, signal, args? }` |
| `widget.screenshot` | server → app | `{ windowId? }` |

Errors carry a numeric `McpErrorCode` (internal, no-app-connected, app-not-found, widget-not-found, connection-write-failed, ipc-timeout, invalid-request, method-not-found) plus a message and optional structured `data`. The `McpError` class is exported from the package index, along with the three factory functions the app-side client needs — `invalidRequestError`, `methodNotFoundError`, and `widgetNotFoundError` — so the app can construct the same error shapes. The remaining factories (`noAppConnectedError`, `appNotFoundError`, `connectionWriteFailedError`, `ipcTimeoutError`) are server-internal and not re-exported.

## Transport layer

`JsonStreamTransport` is the per-connection protocol engine, used on both server and app sides:

- **Framing** — buffers incoming bytes and splits on newlines; blank lines are skipped.
- **Parsing** — each line is JSON-parsed, then classified as a request (has a string `method`) or a response and validated by the matching Zod schema. Unparseable or malformed lines surface as an `invalid` event carrying an invalid-request error.
- **Correlation** — `sendRequest(method, params, timeout)` writes a framed request keyed by a random id and returns a promise stored in a pending map, armed with a per-request timeout. An incoming response resolves or rejects the matching pending promise; a response with an `error` rejects with a reconstructed `McpError`.
- **Closure** — if the underlying writer is not writable, `sendRequest` rejects with `TransportClosedError`; `rejectPending` fails all in-flight requests at once (used on close and shutdown).

`fromSocket` adapts a Node `net.Socket` into a transport, feeding socket `data` into the framer and wiring `close`/`error`.

### Connection bookkeeping

Two layers sit between the socket and the tool handlers:

- **`ConnectionRegistry`** (implements `AppTransport`) is the low-level connection store. For each accepted socket it creates a `JsonStreamTransport`, tracks it by a generated id, re-emits the transport's `request`/`disconnection`/`error` events upward, and answers malformed frames with an invalid-request response. `closeAll`/`clear` support shutdown.
- **`ConnectionManager`** is the app-level router. It owns the set of registered apps keyed by `applicationId`, maps socket connection ids to apps, handles `app.register`/`app.unregister`, and routes outbound tool requests via `sendToApp`. It emits `appRegistered`/`appUnregistered`.

`sendToApp(applicationId, method, params)` resolves a target app — the named app, or the first registered app when `applicationId` is omitted — then issues the request through that app's transport. If the write fails (`TransportClosedError`), the app is removed and a connection-write-failed error is thrown. `waitForApp` resolves immediately if an app is already registered, otherwise waits for the next `appRegistered` event up to a timeout.

## Socket lifecycle and single ownership

`SocketServer` manages the listening socket. On `start()`, if the socket file already exists it probes it: if another live server answers, it refuses to start (error pointing at the conflicting session); otherwise it treats the file as stale and unlinks it before binding. Only one MCP server can own a socket path at a time. `stop()` rejects all pending requests, closes the listener, unlinks the socket file, and clears the registry.

## Tool catalog

`buildTools` produces the AI-facing tools registered on the `McpServer`. Each tool has a Zod `inputSchema`; tools that target a widget or app accept an optional `applicationId`, and when it is omitted the request goes to the first registered app.

| Tool | Forwarded method | Result |
| --- | --- | --- |
| `gtkx_list_apps` | `app.getWindows` per app | JSON: apps + their windows |
| `gtkx_get_widget_tree` | `widget.getTree` | pretty-printed widget tree text |
| `gtkx_query_widgets` | `widget.query` | JSON: matching serialized widgets |
| `gtkx_get_widget_props` | `widget.getProps` | JSON: one serialized widget |
| `gtkx_click` | `widget.click` | ack string |
| `gtkx_type` | `widget.type` | ack string |
| `gtkx_fire_event` | `widget.fireEvent` | ack string |
| `gtkx_take_screenshot` | `widget.screenshot` | base64 PNG image content |

`gtkx_list_apps` additionally accepts `waitForApps`/`timeout` to block until at least one app registers — useful while an app is still starting.

### Forwarding helpers

A small set of helpers builds these tools from a declaration. `defineTool` registers a typed handler on the MCP server. `forwardTool` strips the optional `applicationId` from the args, forwards the rest as IPC params (or a custom mapping), and shapes the app's reply. The reply-shaping variants are `forwardJson` (stringify the result as text), `forwardAck` (discard the result, return a fixed acknowledgment string), and `forwardImage` (return base64 image content from `{ data, mimeType }`).

## Widget identity

Widget IDs are **not** stable GTK handles. They are assigned by the app-side `WidgetRegistry`, which lazily hands out incrementing string ids via a `WeakMap` keyed by widget. Before answering any request the app calls `refresh()`, which rebuilds the id→widget lookup by walking toplevel windows and their child chains. IDs are therefore only meaningful relative to a recent tree/query call against the same connected app; a refresh does not reassign an id already given to a widget, but the lookup table is rebuilt each time.

## How the app fulfils requests

The app-side counterpart lives in the CLI (`packages/cli/src/mcp`) and is started by the dev runner as an embedded `McpClient`. It connects to `DEFAULT_SOCKET_PATH`, sends `app.register { applicationId, pid }`, and answers server-initiated requests. On socket close it auto-reconnects after a delay; on disconnect it best-effort sends `app.unregister`.

For each incoming request the client refreshes its `WidgetRegistry`, resolves the default `Gtk.Application`, and dispatches to a handler. Handlers fulfil the contract using the gtkx testing module (`findAllByRole`/`Text`/`Name`/`LabelText`, `userEvent.click`/`type`/`clear`, `fireEvent`, `screenshot`, `prettyWidget`) and project widgets into the `SerializedWidget` shape — `{ id, type, role, name, text, sensitive, visible, cssClasses, children }` — defined by this package.

## End-to-end flow

```
AI client ──(MCP stdio)──> McpServer ──> tool handler
                                              │ sendToApp(applicationId, method, params)
                                              ▼
                                    ConnectionManager ──> JsonStreamTransport.sendRequest
                                              │  {id, method, params}\n   (NDJSON, Unix socket)
                                              ▼
                                    gtkx app  McpClient
                                              │ refresh registry, dispatch handler
                                              │ (testing utils + serializeWidget)
                                              ▼
                                    {id, result}\n  ──> transport correlates by id
                                              ▼
                              tool shapes reply (JSON / ack / image) ──> AI client
```

On socket close or a failed write the app is dropped (`appUnregistered`) and its pending requests are rejected; the app-side client reconnects and re-registers.

## Package surface

The index re-exports the protocol contract for the app-side client to reuse:

- `DEFAULT_SOCKET_PATH` — the rendezvous socket path.
- `IpcRequest` — the request message type; the `IpcMethod` method-name union (a TypeScript union type, not an enum).
- `ServerRequestParamsSchemas` and `ServerRequestParams` — the per-method param schemas and their inferred types.
- `SerializedWidget` — the widget projection shape.
- `WireParamsSchema` — the structural param-schema interface.
- The `McpError` class with its `McpErrorCode` codes, plus the three factory functions the app-side client needs (`invalidRequestError`, `methodNotFoundError`, `widgetNotFoundError`).
- `JsonStreamTransport` with `TransportClosedError`.

`RegisterParamsSchema`, `IpcResponse`, `IpcMessage`, and the remaining error factories are defined in `protocol/` and consumed internally (e.g. by `connection-manager.ts`), but are not part of the package's public surface. `createMcpServer` and its `McpServerHandle` similarly stay internal to `server.ts`.
