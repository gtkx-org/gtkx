# Tooling policy

The required configuration checks run actionlint 1.7.12, ShellCheck, and Docker build checks. Composite action shell bodies are checked as well as workflow steps and tracked shell scripts. Toolchain declarations are checked for agreement across mise, package metadata, Docker, Sonar, and the sanitizer and minimum-runtime scripts. PyYAML 6.0.3 is installed into the job's temporary directory to read composite metadata. The two actionlint exceptions cover GitHub's release concurrency `queue` property until actionlint supports it; they do not suppress other workflow syntax findings.

Run `mise exec -- bash scripts/check-tooling.sh` in a workstation that provides ShellCheck and PyYAML through the workstation Ansible configuration. Docker build checks run on the GitHub runner. Do not run the repository's container checks through a development container's remote host engine.

Cargo-audit 0.22.2 checks the committed native Cargo.lock through CI on pull requests and main, weekly, when dispatched, and during release verification. CI calls the reusable maintenance workflow so dependency changes do not start a duplicate audit workflow. Vulnerabilities and unsoundness advisories fail the check. Unmaintained and yanked dependency warnings remain visible for review. Each run refreshes the RustSec database and retains its machine-readable report for fourteen days.

The advisory allowlist in `.cargo/audit.toml` is empty. A proposed exception must name one advisory ID, document affected versions and why the shipped code is unaffected or temporarily accepted, name a maintainer responsible for remediation, and set a review date. Record that rationale in this document with the exception change; remove the exception when the dependency is fixed. Severity thresholds and broad advisory exclusions are not used.

The normal Knip check covers development and production usage. The additional strict production check discovers published workspaces from package manifests, excludes test and tooling files, and preserves public entry exports for downstream consumers. Generated GIR/JSX modules, runtime-selected CLI peers, and the Cairo package named in generated imports have narrowly scoped dependency exceptions.

Dependencies have a one-day release cooldown. GTKX's own packages are excluded so local-registry release rehearsals can install the versions they just published. `verifyDepsBeforeRun` stays disabled because those rehearsals intentionally rewrite native manifests and the lockfile temporarily; CI verifies dependencies with a frozen install before executing tasks.

Native dependency updates must also review the retained `cargo-licenses.json` inventory. Check the SPDX expression and any license file for every added or changed crate against GTKX's MPL-2.0 distribution and notice obligations. Missing or custom license declarations require maintainer review before merge. The inventory makes that review reproducible; advisory results do not imply license approval.

PR linting and typechecking use Nx affected execution. A planning job selects ordinary test groups before their matrices start. Shared tooling changes force a full selection; source changes retain complete workspace coverage. Main, manual, and weekly CI runs verify the full workspace. The Nx SHA action uses the PR merge base for PRs and the last successful main push for other events; release version plans retain their separate PR review range.

CI resolves one immutable image digest for every job. Weekly CI refreshes system packages with an uncached build; successful main verification records the digest for release and compatibility jobs and promotes it to `latest`. Forks that change the image upload an architecture-specific archive once and subsequent jobs load it. A failed registry pull fails the job. Rebuilds are explicit through CI's `refresh_image` input.

Fork PRs execute unprivileged verification without the Sonar token. Authenticated Sonar jobs are skipped for those forks and the required external Sonar check remains pending. Until a separate trusted scan-only service is configured and verified, a maintainer must review the contribution, place the reviewed changes on a repository branch, and open a corresponding internal PR for authenticated analysis and normal merge checks. Do not run fork installation, build, or test commands in a privileged `pull_request_target` or `workflow_run` job. Read-only repository metadata confirms a separate Dependabot `SONAR_TOKEN` is configured. The initial Dependabot image rebuild still requires a hosted rehearsal; the image jobs explicitly request package-write permission.
