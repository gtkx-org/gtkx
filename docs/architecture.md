# GTKX Architecture

This document describes how the GTKX monorepo is organized and where each
responsibility lives. The authoritative list of packages is
[`pnpm-workspace.yaml`](../pnpm-workspace.yaml); the table below summarizes the
role of each.

## Package overview

| Package   | Purpose                                              |
| --------- | --------------------------------------------------- |
| `native`  | Rust native module (napi-rs)                        |
| `ffi`     | TypeScript FFI bindings to GTK/GLib                  |
| `react`   | React reconciler for GTK widgets                     |
| `css`     | CSS-in-JS styling for GTK                            |
| `codegen` | Code generation from GIR files                       |
| `cli`     | CLI tooling                                          |
| `mcp`     | MCP server for AI integration                       |
| `testing` | Test utilities                                       |
| `utils`   | Cross-package utilities shared by runtime entry points |
| `e2e`     | End-to-end tests (reconciler nodes)                 |
| `vitest`  | Vitest plugin for GTKX testing                       |

## Native module (`packages/native`)

The Rust native module contains the **transport and GObject identity
primitives** that cannot be implemented purely from generated FFI bindings:

- **JS ↔ GLib thread communication** (dispatch between JavaScript and the GTK main loop)
- **Value marshaling** (converting between JS and GLib types)
- **Trampolines** (callback wrappers for signal handling)
- **GObject identity primitives**: `findObjectProperty`, `getInstanceGType`, `registerClass` — operations that need to introspect the live GObject type system at runtime, not just call generated symbols.

Beyond the primitives listed above, the native module does not contain
GTK/GLib-specific bindings — those are all in `@gtkx/ffi`. It has been
thoroughly tested with hundreds of FFI calls, so it should not be the first
place to investigate when debugging.

## FFI package (`packages/ffi`)

Contains all FFI bindings to GTK/GLib libraries, organized into three layers:

1. **Generated bindings (`src/generated/`)** — every GTK/GLib/Adw class, method, property, and signal whose definition lives in `/girs`. Gitignored; use `grep`/`find` in the terminal (Glob won't see them). Regenerated by `turbo codegen`. If an API is in the GIR, it is here.
2. **Runtime infrastructure (`src/lifecycle.ts`, `src/registry.ts`, `src/handles.ts`, `src/native.ts`, `src/object.ts`, `src/gobject/*`, `src/runtime.ts`, …)** — process-level wiring that glues the generated bindings to `@gtkx/native`: GType registry, object identity, GValue marshalling, signal/event plumbing, freeze/unfreeze, class registration. Hand-written and not derivable from GIR.
3. **GIR-less extensions (`src/gl/gl.ts`, `src/cairo/*.ts`, prototype augmentations like `scrolled-window.ts:scrollTo`)** — APIs that have no GIR coverage (Cairo, GL) or that need GIR-incompatible extensions. Also hand-written.

To tell whether a piece of FFI code is generated or hand-written, look at its
location: anything outside `src/generated/` is hand-written.

## React package (`packages/react`)

The React reconciler for GTK:

- Does not contain FFI bindings (those are in `packages/ffi`).
- Does not contain React components (no `<MyComponent>` wrappers).
- Does not contain tests (they are in `packages/e2e`).
- All GTK/Adw elements are implemented as **specialized reconciler nodes** in `src/nodes/`.
- JSX intrinsic elements (`<GtkButton>`, `<AdwWindow>`, etc.) are **autogenerated** in `src/generated/`.

## CSS package (`packages/css`)

All CSS styling must use `@gtkx/css`. Do not use inline styles or other CSS
approaches.

## Code generation

GIR files in `/girs` are processed by `packages/codegen` to generate:

1. FFI bindings in `packages/ffi/src/generated/`
2. JSX intrinsic types in `packages/react/src/generated/`

Run codegen with `turbo codegen`.
