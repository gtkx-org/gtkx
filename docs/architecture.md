# GTKX Architecture

This document describes how the GTKX monorepo is organized and where each
responsibility lives. The authoritative list of packages is
[`pnpm-workspace.yaml`](../pnpm-workspace.yaml); the table below summarizes the
role of each.

## Package overview

| Package   | Purpose                                              |
| --------- | --------------------------------------------------- |
| `native`  | Rust native module (napi-rs)                        |
| `ffi`     | Hand-written FFI runtime (GValue/GType, identity, lifecycle) |
| `react`   | React reconciler for GTK widgets                     |
| `css`     | CSS-in-JS styling for GTK                            |
| `codegen` | Code generation from GIR files                       |
| `cli`     | CLI tooling                                          |
| `mcp`     | MCP server for AI integration                       |
| `testing` | Test utilities                                       |
| `utils`   | Cross-package utilities shared by runtime entry points |
| `e2e`     | End-to-end tests (reconciler nodes)                 |
| `vitest`  | Vitest plugin for GTKX testing                       |

## Native module (`packages/native`)

The Rust native module contains the **transport and GObject identity
primitives** that cannot be implemented purely from generated FFI bindings:

- **JS ↔ GLib thread communication** (dispatch between JavaScript and the GTK main loop)
- **Value marshaling** (converting between JS and GLib types)
- **Trampolines** (callback wrappers for signal handling)
- **GObject identity primitives**: `findObjectProperty`, `getInstanceGType`, `registerClass` — operations that need to introspect the live GObject type system at runtime, not just call generated symbols.

Beyond the primitives listed above, the native module does not contain
GTK/GLib-specific bindings — those are generated into `@gtkx/gi` (see Code
generation), built on the hand-written `@gtkx/ffi` runtime. It has been
thoroughly tested with hundreds of FFI calls, so it should not be the first
place to investigate when debugging.

## FFI package (`packages/ffi`)

A pure, hand-written runtime that the generated `@gtkx/gi` bindings build on. It
imports **zero** generated code, giving a strictly one-way `gi → ffi` dependency
graph. Two layers:

1. **Runtime infrastructure (`src/lifecycle.ts`, `src/registry.ts`, `src/handles.ts`, `src/native.ts`, `src/object.ts`, `src/gobject/*`, `src/runtime.ts`, …)** — process-level wiring that glues the bindings to `@gtkx/native`: GType registry, object identity, GValue marshalling (hand-bound `g_value_*` / `g_type_*`), signal/event plumbing, freeze/unfreeze, class registration. Not derivable from GIR.
2. **The single `@gtkx/ffi` barrel (`src/index.ts`)** — the one specifier the generated bindings and their augment overlay import at load and call time.

The generated GTK/GLib/Adw bindings themselves live in `@gtkx/gi`, not here, and
the GIR-less extensions (Cairo, GL, prototype augmentations) live in the codegen
augment overlay (see Code generation).

## React package (`packages/react`)

The React reconciler for GTK:

- Does not contain FFI bindings (those are in `packages/ffi`).
- Does not contain React components (no `<MyComponent>` wrappers).
- Does not contain tests (they are in `packages/e2e`).
- All GTK/Adw elements are implemented as **specialized reconciler nodes** in `src/nodes/`.
- JSX intrinsic elements (`<GtkButton>`, `<AdwWindow>`, etc.) are **autogenerated** into the injected `@gtkx/react-jsx` package and re-exported by `@gtkx/react` (see Code generation).

## CSS package (`packages/css`)

All CSS styling must use `@gtkx/css`. Do not use inline styles or other CSS
approaches.

## Code generation

GIR files in `/girs` are processed by `packages/codegen` to materialize two
self-contained, **codegen-owned** packages into a hidden `node_modules/.gtkx`
store, each exposed through a visible `node_modules/@gtkx/<name>` symlink:

1. **`@gtkx/gi`** — the generated GObject-Introspection bindings (`@gtkx/gi/gtk`, `@gtkx/gi/glib`, …), the public surface consumed by `@gtkx/react` and end users. Assembled from the raw generated modules plus the hand-written augment overlay in `packages/codegen/overlay/` (the `gl`/`cairo`/`graphene`/`gobject` extensions and prototype patches with no GIR coverage or GIR-incompatible additions). Gitignored; use `grep`/`find` in the terminal (Glob won't see them).
2. **`@gtkx/react-jsx`** — the generated `jsx`/`internal`/`compounds` modules, re-exported by `@gtkx/react`.

The injected packages are regenerated by `gtkx dev` / `gtkx build` and the
`@gtkx/cli#codegen` turbo task, so codegen never mutates store-owned folders.
Regeneration is conditional: `gtkx codegen` (the default) regenerates only when
the store is missing or its fingerprint sentinel is stale — a changed library
set, GIR runtime, or `@gtkx/codegen` version. `gtkx codegen --force` wipes and
regenerates unconditionally (recovery for a corrupted store). `gtkx dev` also
watches `gtkx.config.ts` and regenerates plus restarts the dev runner when it
changes (e.g. an edited `libraries` list). Because the packages are a generated
build artifact and not declared dependencies, consumers import `@gtkx/gi` /
`@gtkx/react-jsx` without listing them in `package.json`; knip resolves them as
the `.gtkx/gi` and `.gtkx/jsx` workspaces (registered through the `.gtkx` symlink
into `node_modules/.gtkx`), so no `ignoreDependencies` allowance is needed.

Run codegen with `turbo codegen`.
